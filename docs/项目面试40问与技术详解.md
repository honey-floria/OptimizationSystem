## 一、项目定位与实验设计（1—5）

### 01. 请用两分钟介绍这个项目：解决什么问题，核心贡献是什么？

**回答主线：** 这是一个面向金融数值问答的模型优化实验系统。它在业务质量约束下比较量化、混合精度和剪枝方案，并把模型、数据、环境、逐样本预测和性能证据关联起来。重点是建立可以判断“是否值得部署”的闭环。

**技术细节：** 流程为输入校验 → 高精度基线 → 业务质量诊断与修复 → 量化对比 → 层与模块敏感性分析 → 真实低比特制品导出 → 质量与性能门禁。金融任务尤其关心金额、比例、日期和计算结果；通顺的回答不代表数值正确，因此不能只看困惑度或文本相似度。

我会把贡献概括为三点：统一评测口径；从整体准确率下钻到样本和模块；用真实制品和性能数据检验研究假设。项目最终没有强行选择更复杂的保护方案，而是保留通过门禁的 Linear INT4 基线，这体现了实验决策能力。

**可能追问：** 项目是不是 RAG 系统？当前主线是模型优化与评测，知识库构建、向量检索和业务规则制定不属于已交付的核心能力。

**代码与证据：** [README](../README.md)、[业务范围配置](../configs/business_scope.json)、[阶段验收](../src/quantization/stage7_acceptance.py)。

### 02. 为什么先做金融业务质量基线，而不是直接压缩模型？

**回答主线：** 压缩通常是在既有能力上做取舍，不能把低质量基线包装成优化成功。基线既要能运行，也要能有效完成目标任务。

**技术细节：** 项目早期 0.5B FP16 基线业务质量只有约 0.91%，已在进度材料中明确不能作为生产基线。若候选同样接近零准确率，即使“相对基线不退化”，也没有实际业务价值。应分别设置绝对质量门槛、相对退化门槛和关键样本门槛。

后续先排查上下文、输出解析、算术和容量问题，再做 7B QLoRA 修复并冻结母版。这样量化实验才能回答“压缩造成了哪些变化”，而不是把原始模型缺陷和压缩误差混在一起。7.4 的候选非退化比较基准是真实全 Linear INT4；它不是相对原始 FP16 的无损证明。

**可能追问：** 阶段门禁通过是否意味着生产可用？不意味着。它只证明满足该阶段冻结的条件，仍需业务绝对质量验收和部署验证。

**代码与证据：** [进度与基线边界](TODO.md)、[基线诊断](../src/evaluation/baseline_quality_diagnosis.py)、[质量修复](../src/evaluation/quality_repair.py)。

### 03. 项目架构怎么划分，怎样降低不同实验之间的耦合？

**回答主线：** 按资产校验、推理服务、评测、性能测试、优化算法和验收拆分。配置描述实验，manifest 描述制品，报告承载证据。

**技术细节：** `src/input_validation` 校验模型、数据和硬件；`BaselineService` 封装模型与 tokenizer；`src/evaluation` 实现数值评分、修复实验和错误定位；`src/benchmark` 统一性能矩阵；`src/quantization` 负责各量化路径和候选筛选；`src/pruning` 负责结构删减。脚本层承担执行编排。

不同后端可以加载不同格式的权重，但对外继续使用统一推理和评测结构。这能减少“每接一种算法就重写一套评分”的风险。也要承认当前代码仍有路径处理、JSON 读写、证据登记的重复实现；后续可抽成共享的资产与运行上下文组件，但需要保持已有报告格式兼容。

**可能追问：** 为什么不一开始做复杂服务化？当前瓶颈是实验正确性和证据闭环，离线 CLI 更便于复现；在线调度可在候选稳定后引入。

**代码与证据：** [目录说明](PROJECT_STRUCTURE.md)、[统一服务](../src/baseline/service.py)、[Benchmark](../src/benchmark/runner.py)。

### 04. 校准集、训练集、验证集和回归集有什么区别？如何防止数据泄漏？

**回答主线：** 训练集用于学习参数，校准集用于确定量化统计或尺度，验证集用于比较方案，回归集用于检查关键行为，最终测试集应保留为独立验收资产。

**技术细节：** QLoRA 脚本从训练资产中按固定种子划出 holdout，默认比例 5%；量化资产校验检查声明的文件、字段、哈希和相关集合重叠。敏感性分析还冻结样本索引与内容指纹，避免候选使用了不同难度的子集。

现有重叠检查基于问题等信息，不能等价于完整语义去重。同一财报改写问题、同一表格换问法仍可能跨集合出现。更严格的设计可以按文档、公司和年份分组切分，再做规范化文本与语义近重复检查。高风险集或长上下文集如果来自 dev，应将它们称为同一资产的切片，不能当作三份独立样本量相加。

**可能追问：** 反复在 dev 上挑层会不会过拟合？会。候选预注册只能减少事后挑选，最终仍需要独立测试集检验泛化。

**代码与证据：** [数据校验](../src/input_validation/dataset_input.py)、[数据构建](../src/data/finqa_assets.py)、[QLoRA 训练](../scripts/train_finqa_qlora.py)。

### 05. 怎样保证量化结果可复现、可追溯？设随机种子够吗？

**回答主线：** 种子只是其中一项，还需要冻结输入资产、模型母版、生成设置、运行环境和实验合同。

**技术细节：** 应记录权重 SHA256、tokenizer、数据内容与索引哈希、提示模板、生成参数、量化配置、依赖版本和硬件信息。项目以 manifest、environment lock、预测文件与 evidence receipt 连接这些证据。混合精度收口还重新计算候选合同哈希，发现 prepare 之后候选定义变更就拒绝继续沿用旧合同。

`do_sample=false`、单 beam 和固定 seed 能减少生成随机性，但跨设备、不同 kernel 和浮点归约顺序仍可能引发差异。因此“相同环境重复运行一致”和“跨后端逐 token 一致”是两个不同目标。哈希验证能证明内容一致性，不能单独证明来源可信，也不保证统计结论正确。

**可能追问：** 环境版本一致为什么仍会变？需要进一步检查模型文件、编译设置、GPU 架构、输入顺序和底层算子实现。

**代码与证据：** [环境锁定](../src/environment_lock/manager.py)、[敏感性准备](../src/quantization/layer_sensitivity_setup.py)、[混合精度收口](../src/quantization/mixed_precision.py)。

## 二、基线、数值评测与 QLoRA（6—12）

### 06. FP16、BF16 和 INT4 分别表示什么？为什么同一项目会同时使用它们？

**回答主线：** FP16/BF16 是浮点格式，INT4 是低比特整数编码；存储精度、计算精度和 KV Cache 精度需要分别说明。

**技术细节：** FP16 的指数位为 5、尾数位为 10；BF16 的指数位为 8、尾数位为 7。BF16 范围更大，但在相同量级下有效精度更低。它不天然保证更高业务准确率。最终 TorchAO 配置使用 INT4/INT8 weight-only，计算 dtype 为 BF16，Embedding、Norm 和 KV Cache 保持 BF16。

因此 `all_linear_int4` 不是每个张量都占 4 bit，也不是所有算术都用 4 bit。目录中的 `merged-fp16` 名称同样不能替代实际加载 dtype 检查。比较两套实验时应同时报告源权重、加载 dtype、计算 dtype、累加行为和 cache dtype，避免把格式切换造成的差异误认为算法收益。

**可能追问：** BF16 是否一定更快？取决于设备与 kernel；格式属性不能直接推出实测延迟。

**代码与证据：** [基线配置](../configs/baseline.json)、[真实混合精度配置](../configs/mixed_precision_search.json)。

### 07. 推理基线怎样固定生成行为，为什么 token 预算会影响实验结论？

**回答主线：** 固定提示模板、上下文、截断长度和解码参数，才能把差异主要归因于候选模型。

**技术细节：** 基线配置包含 `seed=42`、`max_input_tokens=4096`、`do_sample=false`、`num_beams=1`，默认生成 32 token。但质量修复的结构化输出需要更长预算，实际实验必须查看该实验的配置和运行报告，不能把默认 32 token 套用到所有任务。

金融题的表格可能在上下文末尾，截断会删除关键证据；输出预算不足会导致 JSON 缺括号、公式不完整或答案缺失。比较候选时应检查输入是否一致、输出是否提前 EOS、解析失败是否集中在触及上限的样本。性能测试则显式设置相同的最小和最大输出长度，避免一个模型更早结束被误判为更快。

**可能追问：** greedy decoding 能否消除全部不确定性？不能，浮点与后端差异仍可能改变非常接近的 token 排序。

**代码与证据：** [推理服务](../src/baseline/service.py)、[质量配置](../configs/quality_repair_4080.json)、[性能采样](../src/benchmark/runner.py)。

### 08. 金融数值答案怎么评分？为什么不用普通字符串 Exact Match？

**回答主线：** 数值答案需要处理逗号、百分号和格式差异，再按统一数值口径判断；格式正确与业务正确要分开统计。

**技术细节：** `parse_numeric_answer()` 用正则提取数字，去掉千位分隔符后转为 `Decimal`，紧随的百分号会触发除以 100。`evaluate_numeric_answers()` 默认使用绝对容差 `1e-4`，分开返回 `parse_rate` 与 `numeric_accuracy`。例如 `12.5%` 和 `0.125` 可归一为同一数值。

`Decimal` 减少二进制浮点表示对十进制比较的干扰，但不能解决语义问题。当前基础解析器会提取第一个匹配数字，含“2020 年增长 12.5%”的自然语言可能误取年份；也不是完整的货币、科学计数法、会计括号负数解析器。项目通过结构化输出减少这种歧义，更严格的业务评分还应单独检查币种、量纲与数量级。

**可能追问：** 为什么不总用相对误差？零值附近不稳定；可设计绝对与相对容差组合，但需业务确认并冻结，不能为提高分数临时放宽。

**代码与证据：** [数值指标](../src/evaluation/finqa_metrics.py)、[指标测试](../tests/test_finqa_metrics.py)。

### 09. 为什么要求输出 evidence、formula、value、unit？调用计算器能解决哪些错误？

**回答主线：** 把证据选择、运算选择、算术执行和格式输出拆开，才能定位错误来源。计算器可以修复算术，不能替模型保证选对证据和公式。

**技术细节：** 训练目标包含 `evidence`、`formula`、`value`、`unit`。质量修复模块还探索了稳定表格单元格 ID、操作类型和多步计算，使程序可以检查引用的单元格是否存在、操作数是否有效，以及计算过程是否满足支持的约束。

例如 `(本年利润-上年利润)/上年利润` 即使计算器算得完全正确，若模型引用了收入行而非利润行，业务答案仍然错误。安全计算实现采用受限语法解析与允许的运算，避免直接执行任意 `eval`。结构化字段也只是可验证的外显信息，不能保证它就是模型真实内部推理过程。

**可能追问：** 能不能解析失败时从参考答案补值？不行，参考答案只能参与评分；任何修复都必须依据模型输出和允许的题目上下文。

**代码与证据：** [结构化解析与安全计算](../src/evaluation/quality_repair.py)、[修复测试](../tests/test_quality_repair.py)。

### 10. 为什么选 QLoRA？它与 LoRA、推理量化的区别是什么？

**回答主线：** LoRA 用低秩增量训练少量参数，QLoRA 再将冻结基座以低比特方式加载以减少训练显存。它首先解决适配训练成本，并不直接交付目标推理后端的 INT4 制品。

**技术细节：** 对线性层权重可写成 `W_eff = W_base + (alpha/r) × B × A`，其中 `A`、`B` 为可训练低秩矩阵。项目训练默认 `r=8`、`alpha=16`、dropout 为 0.05，目标包含 Q/K/V/O 与 MLP 的 gate/up/down 七类投影。

基座采用 bitsandbytes NF4、FP16 计算和 double quant；优化器为 `paged_adamw_8bit`，开启 gradient checkpointing，单卡 micro-batch 为 1、默认梯度累积 16 步。单卡条件下名义有效 batch 为 16 条，但不同样本的 token 数仍不同。NF4 训练加载格式与最终 TorchAO INT4 packing、AWQ/GPTQ 格式不能混为一谈。

**可能追问：** 为什么冻结的输入还要 `enable_input_require_grads()`？它用于保证相关训练与 checkpointing 路径中的梯度传播，不意味着将全部基座权重解冻。

**代码与证据：** [QLoRA 训练实现](../scripts/train_finqa_qlora.py)。

### 11. 监督微调为什么要把 prompt 和 padding 的 label 设成 -100？有哪些隐藏问题？

**回答主线：** 目标是让 loss 主要约束回答部分，避免模型把大量容量用于复述提示；`-100` 是常用交叉熵忽略标签。

**技术细节：** `SupervisedDataset` 分别 tokenize prompt 和完整文本，把 prompt 对应 label 置为 `-100`。`CausalCollator` 将 padding 的 attention mask 置零、label 置为 `-100`。完整文本末尾附 EOS，帮助模型学习答案结束。

两个边界值得主动说明。第一，prompt 太长时，截断可能删掉全部 target，留下所有 label 都是 `-100` 的无效样本。第二，分别 tokenize prompt 与拼接后的文本，边界 token 化不一定严格保持前缀一致，可能造成一个或多个 token 的遮罩偏移。建议检查有效监督 token 数，过滤空监督样本，并采用可靠的模板边界或 token 级拼接策略。

**可能追问：** 如何排查 `eval_loss=null`？先检查有效标签数、loss 是否 NaN、截断分布和日志序列化，再排查数值稳定性；不能在没有证据时认定某个原因就是本项目根因。

**代码与证据：** [Dataset 与 Collator](../scripts/train_finqa_qlora.py)、[训练测试](../tests/test_finqa_qlora.py)、[待修复项](TODO.md)。

### 12. 为什么先合并 adapter、冻结高精度母版，再进行敏感性分析？

**回答主线：** 必须保证所有量化候选来自相同的有效模型，避免候选之间同时存在 adapter、基座和量化方式差异。

**技术细节：** LoRA 增量与高精度基座合并后，形成固定的 `W_base + ΔW`。后续方案再从这个母版出发施加不同精度策略。项目准备流程区分数学参考 `ref_fp` 和已接受的 QLoRA/NF4 业务参考 `ref_nf4`，并记录母版 manifest 和冻结子集。

不能假设原 NF4+adapter 推理与高精度合并后再量化逐 token 等价：量化不是线性运算，一般有 `Q(W + ΔW) ≠ Q(W) + ΔW`。因此要先验证合并模型的质量，再把 fake-quant 与真实后端差异单独测出来。checkpoint、adapter、母版和导出制品都应分别标识，避免只凭目录名称判断版本。

**可能追问：** 合并后分数变化怎么办？先检查基座版本、adapter 哈希、合并 dtype、tokenizer 与生成设置，然后做逐样本配对分析。

**代码与证据：** [层级实验准备](../src/quantization/layer_sensitivity_setup.py)、[准备脚本](../scripts/prepare_layer_sensitivity.py)。

## 三、量化原理与真实制品（13—20）

### 13. INT4 量化的数学原理是什么？误差来自哪里？

**回答主线：** 用有限离散编码近似连续权重，主要误差来自舍入、裁剪和尺度选择。

**技术细节：** 常见均匀仿射量化可表示为 `q = clip(round(w/s) + z, q_min, q_max)`，反量化为 `w_hat = s × (q-z)`。`s` 是 scale，`z` 是 zero point。对称量化通常固定中心并简化零点处理；非对称量化可更充分利用偏斜分布的编码区间，但需要额外元数据与算子支持。

4 bit 只有 16 个编码值，异常大权重会拉大组内尺度，使普通权重的分辨率下降；裁剪异常值又会引入截断误差。最终影响取决于输入激活及后续非线性，最小权重 MSE 不保证金融正确率最高。这里的公式是通用解释，具体 TorchAO、AWQ、GPTQ 路径的编码、范围与 packing 需以制品实现为准。

**可能追问：** 有 zero point 是否就一定更准？不一定，还要看分布、粒度、校准目标与 kernel 约束。

**代码与证据：** [fake-quant 实现](../src/quantization/layer_sensitivity.py)、[量化框架](../src/quantization/framework.py)。

### 14. per-tensor、per-channel、group-wise 有什么区别？group size 如何影响收益？

**回答主线：** 量化粒度决定多少权重共享一个 scale；粒度越细通常越能适应局部分布，但元数据和计算处理开销也可能增加。

**技术细节：** per-tensor 为整张量共享尺度，per-channel 通常为一个输出通道一组尺度，group-wise 在指定维度进一步分组。项目真实 INT4 配置的 group size 为 32。假设每组仅额外保存一个 16 bit scale，那么理想平均存储为 `4 + 16/32 = 4.5 bit/weight`；若还有 zero point、padding 与 packing 对齐，开销更大。这个公式只作开销示例，不是对实际制品格式的断言。

比较 group size 不能只看理论 bit 数，应同时检查质量、制品大小、GPU 峰值和算子支持。更小的 group 在某后端上可能破坏高效矩阵布局，带来更慢的反量化和访存。

**可能追问：** 为什么不直接选最小 group？最小误差、最小显存和最低延迟往往不是同一个配置。

**代码与证据：** [混合精度配置](../configs/mixed_precision_search.json)、[AWQ 配置](../configs/awq.json)、[GPTQ 配置](../configs/gptq.json)。

### 15. AWQ 和 GPTQ 的核心区别是什么？本项目如何比较它们？

**回答主线：** 两者都可用于低比特权重量化，但优化误差的思路不同。项目重点是接入和验证，而不是声称重新发明算法。

**技术细节：** AWQ 利用激活统计识别重要通道，通过等价缩放等策略保护对输出敏感的权重。GPTQ 使用校准输入构造近似二阶信息，在逐步量化权重时补偿相关误差，目标更接近保持线性层输出。可用 `||WX - W_hat X||²` 理解其重建目标，其中 `X` 来自校准输入。

公平比较需要相同母版、校准来源、生成参数、评测集和硬件，并明确 group size 等差异。还要分开比较离线量化耗时、最终质量和在线性能。本仓库有 AWQ/GPTQ 的计划生成、导出、重载及证据检查；早期阶段对比不能直接与后续 7B QLoRA 模型合并成一张“算法优劣榜”。

**可能追问：** 哪个一定更好？没有脱离模型、数据和后端的统一答案，必须看真实制品与负载。

**代码与证据：** [AWQ 实现](../src/quantization/awq.py)、[GPTQ 实现](../src/quantization/gptq.py)、[对比模块](../src/quantization/comparison.py)。

### 16. SmoothQuant 为什么能缓解激活异常值？W8A8 与 W4A16 怎么选？

**回答主线：** SmoothQuant 在数学等价的前提下，把一部分激活量化难度转移到权重。W8A8 同时量化权重和激活，W4A16 主要压缩权重。

**技术细节：** 对 `Y=XW`，可写成 `Y=(X S^-1)(S W)`，其中 `S` 是沿输入通道的对角缩放矩阵。选择合适尺度能压低激活异常通道的范围，但会扩大相应权重；平衡参数控制难度转移。量化前等价，不意味着量化后无误差。

W4A16 在权重读取占比较高的 decode 负载中可能有优势；W8A8 在硬件支持高效 INT8 GEMM、计算占比较高时可能更合适。项目最终 TorchAO INT8 候选也是 weight-only，不能把它叫做 SmoothQuant W8A8。两条路径必须分开描述。

**可能追问：** W8A8 显存是否必然比 W4A16 高？权重通常更大，但运行峰值还受激活、batch、workspace 和 cache 影响，需要测量。

**代码与证据：** [INT8/SmoothQuant 路径](../src/quantization/int8_fp8.py)、[最终 weight-only 路径](../src/quantization/mixed_precision.py)。

### 17. 为什么不能只根据显卡型号或 dtype 存在判断 FP8 可用？

**回答主线：** FP8 可用性是硬件、软件、算子、模型路径和性能收益共同决定的，需要逐层验证能力。

**技术细节：** dtype 常量存在只代表库能表达这种类型，不代表目标设备能高效执行 FP8 矩阵乘。项目包含能力信息采集和 FP8 matmul probe，用实际执行结果区分“类型可见”和“算子可运行”。之后还要验证完整模型是否存在 fallback、是否满足布局和缩放要求。

FP8 的不同编码也存在范围与精度取舍；缩放策略和异常值处理决定误差。最终应检查模型生成正确性、业务回归、profile 与性能数据。当前项目材料不能被扩展成“所有 NVIDIA 设备均完成 FP8 优化”。

**可能追问：** probe 成功能否直接上线？不能，小矩阵算子运行成功只证明局部能力，不涵盖完整模型、长上下文和并发负载。

**代码与证据：** [FP8 probe](../src/quantization/int8_fp8.py)、[硬件输入校验](../src/input_validation/hardware_input.py)。

### 18. fake-quant 与真实 INT4 权重有什么区别，为什么两种实验结论可能相反？

**回答主线：** fake-quant 用浮点张量模拟量化误差，真实量化还涉及压缩存储、打包格式和实际执行算子，两者的用途不同。

**技术细节：** fake-quant 常执行 `W_hat=dequantize(quantize(W))`，随后仍以浮点张量保存和计算。它适合快速分析质量敏感性，不能证明真实显存和延迟收益。真实 TorchAO 导出替换 Linear 权重为量化 Tensor 子类，并采用 `tile_packed_to_4d` 布局。

即使同为 INT4，分组、scale、舍入、padding、计算 dtype 和算子路径不同，也会改变后续误差传播。项目实施记录中，fake-quant 组合曾取得正净增，而真实主混合精度候选在 full-dev 相对真实 INT4 净减少 5 题。因此研究阶段用于缩小搜索范围，最终结论必须通过目标后端复测。

**可能追问：** 可以用 fake-quant 文件大小估算部署压缩率吗？只能作理论参数量估算，不能当作真实制品或 GPU 常驻显存证据。

**代码与证据：** [敏感性 fake-quant](../src/quantization/layer_sensitivity.py)、[真实导出](../src/quantization/mixed_precision.py)、[实施记录](PROJECT_DOCUMENTATION.md)。

### 19. 如何证明模型真的被量化，而不是改了配置文件？

**回答主线：** 检查模块级实际权重、序列化制品与重载结果，并把“成功导出”和“可推荐部署”分开。

**技术细节：** `build_module_assignment()` 根据完整模块名生成位宽分配。导出后逐模块比较期望精度、实际观察到的精度和权重类型；如果 INT4/INT8 目标仍是普通浮点 Parameter，或观察到的位宽不符，则导出失败。保存模块清单、文件大小、state_dict SHA256 和后端版本。

加载时检查 SHA256，并严格检查 state_dict 键。仅导出成功的 manifest 仍设置 `deployment_claims_allowed=false`；质量与性能证据齐全、筛选通过之后，最终 ranking 才允许对应声明。权重已低比特驻留也不自动证明每个算子都走最优 kernel，进一步的 kernel 级证明仍需要 profiler。

**可能追问：** 为什么不能直接看 `weight.dtype`？量化 Tensor 子类可能对外暴露逻辑 dtype，真实存储与 packing 需要结合类型和内部格式判断。

**代码与证据：** [位宽审计、导出与加载](../src/quantization/mixed_precision.py)、[混合精度测试](../tests/test_mixed_precision.py)。

### 20. 7B 模型在 16 GiB 显存上导出量化权重，为什么仍可能 OOM？如何解决？

**回答主线：** 最终制品能放下，不代表转换过程的瞬时峰值能放下。量化需要原权重、临时张量和 packed 权重共同占用空间。

**技术细节：** 先将完整 7B BF16 模型搬到 GPU，可能已经消耗接近卡容量；给大矩阵 padding、转置或 packing 时会额外申请空间。项目将高精度母版保留在 CPU，遍历 Linear，逐个调用 `quantize_(..., device=cuda)`，把完成的低比特权重留在 GPU，最后再搬运 BF16 特殊模块。

这样把峰值从“完整高精度模型 + 转换临时空间”改为“已量化部分 + 当前模块转换空间 + 保留模块”，以系统内存换取 GPU 峰值下降。`empty_cache()` 只释放未被活跃张量引用的缓存，不能替代这个数据流改造。CPU 内存、磁盘空间和用户 quota 也必须纳入容量预算。

**可能追问：** 为什么不用最直观的全模型 `.to(cuda)` 后再量化？该流程会在量化开始前就占满显存，后续再小心清 cache 也无法消除活跃权重。

**代码与证据：** [逐 Linear 导出](../src/quantization/mixed_precision.py)、[导出脚本](../scripts/run_mixed_precision_exports.sh)。

## 四、敏感性分析与混合精度选择（21—27）

### 21. 逐层敏感性实验怎么设计，如何保证只改变一个变量？

**回答主线：** 从全 INT4 参考出发，每次只将一个 Transformer block 恢复为 INT8，固定其他条件，比较业务质量恢复量。

**技术细节：** 28 层模型的计划包含两种参考、全 INT4、全 INT8，以及 28 个单层 INT8 候选。`validate_plan_matrix()` 检查层覆盖和唯一性；`validate_plan_isolation()` 比较精度向量，保证每个候选只改变目标层。运行时还应从相同母版构造，不能在已量化模型上反复叠加变换。

项目先用 80 条 pilot 覆盖 28 层，再让预注册的 10、22、23 层进入 883 条 full-dev 确认。这是分阶段控制成本的实验，不是 28 层都完成了 full-dev。报告明确写出 `candidate_subset`，避免扩大结论。

**可能追问：** 为什么不直接全量测所有层？可以，但成本更高；pilot 需要承担筛选偏差，最终报告应保留覆盖范围和独立测试计划。

**代码与证据：** [层级矩阵和隔离检查](../src/quantization/layer_sensitivity.py)、[层级最终报告](../out/layer_sensitivity/final_evaluation/report.md)。

### 22. 为什么权重 MSE 最小的层，不一定是最值得保护的层？

**回答主线：** 权重误差只是局部数值差异，任务正确性还取决于激活分布、误差方向和后续网络传播。

**技术细节：** 对线性层有 `ΔY=ΔW×X`，因此相同的 `||ΔW||` 在不同 `X` 下造成的输出误差不同。项目记录 MSE、归一化误差、余弦相似度、最大绝对误差和饱和率，并采集 block 激活误差。激活采样通过固定位置与冻结参考保证可比性。

计算大张量误差时需要分块和较稳定的累积方式，避免全量差值张量引发额外显存峰值，或低精度求和掩盖差异。排序时优先业务质量，把误差指标用于解释和辅助区分；单个层的激活误差也不能自动证明最终答案错误的因果链。

**可能追问：** 能否直接按参数量最大的层恢复精度？参数量只反映潜在成本，不等价于业务敏感性。

**代码与证据：** [误差统计与激活采集](../src/quantization/layer_sensitivity.py)。

### 23. 从层级分析细化到 Attention 和 MLP，具体怎么做？

**回答主线：** 整层恢复粒度过粗，进一步分别保护 Attention 与 MLP，才能用更少的高精度参数获得可能的质量收益。

**技术细节：** Attention 组包含 `q_proj/k_proj/v_proj/o_proj`；MLP 组包含 `gate_proj/up_proj/down_proj`。模块发现流程检查模型真实结构、shape 和路径，而不是仅凭名称猜测。最终位宽策略按完整 FQN 或模块路径前缀匹配，例如 `model.layers.10.mlp` 覆盖该层 MLP 的三个 Linear。

模块报告中 `layer_10_mlp_int8` 在 fake-quant full-dev 达到 338/883，相对该阶段参考净增 10。它提供了进一步保护 Layer 10 MLP 的依据，但不等于已经证明真实 TorchAO 部署收益。也不能用模块实验中的 338 与另一阶段不同参考的分数直接相减。

**可能追问：** 为什么保护两个有效模块不一定更好？误差相互影响、非线性和生成轨迹变化会导致非可加效应，必须做组合消融。

**代码与证据：** [模块合同](../src/quantization/module_sensitivity.py)、[模块实验](../src/quantization/module_sensitivity_experiments.py)、[模块报告](../out/module_sensitivity/final_evaluation/report.md)。

### 24. Embedding、lm_head、Norm 和 KV Cache 为什么单独处理？

**回答主线：** 这些模块的语义、结构和后端支持不同，不能直接沿用普通 Linear 的位宽策略。

**技术细节：** Embedding 是查表；`lm_head` 将隐藏状态投影到词表 logits，对接近的 token 排名可能敏感；Norm 影响尺度但参数量通常较少；KV Cache 是随序列增长的运行时状态，不是静态权重。Embedding 与 `lm_head` 还可能权重共享，必须检查 storage identity，避免重复计数或不一致修改。

当前真实后端对 Linear 量化，Embedding INT8 研究候选被显式标为 `unsupported`，因为不能证明 `nn.Embedding` 低比特驻留。`all_linear_int4` 实际将 Embedding、Norm、KV Cache 留在 BF16，模型整体仍是混合精度。KV Cache probe 需要检查实际 dtype、存储和回退情况，配置写了 INT8 不等于 cache 已压缩。

**可能追问：** 为什么不把 Norm 也压到 INT4？节省的参数空间可能很小，而误差和 kernel 兼容成本未必值得。

**代码与证据：** [共享权重检查与 KV probe](../src/quantization/module_sensitivity.py)、[候选支持边界](../configs/mixed_precision_search.json)。

### 25. 什么是逐样本配对转移？为什么比只看准确率差值更有解释力？

**回答主线：** 相同总分可能对应完全不同的错误集合，配对分析能看清候选恢复了哪些题、又破坏了哪些题。

**技术细节：** 对同一 sample ID 建立四类：基线对候选对、基线对候选错、基线错候选对、两者都错。设恢复数为 `r`、退化数为 `d`，净正确数变化为 `r-d`，准确率变化为 `(r-d)/N`。

项目真实 INT8 相对 INT4 的 full-dev 是恢复 41、退化 37，净增 4；主混合精度候选是恢复 6、退化 11，净减 5。前者不是“只影响了四道题”，而是 78 道题发生正确性翻转。原始文本发生变化的题数又是另一个指标：答案措辞改变不一定导致正确性改变。

**可能追问：** 净增为零能否认为无风险？不能，高风险题可能被普通题收益抵消，必须按业务切片和关键样本分别检查。

**代码与证据：** [配对转移函数](../src/quantization/layer_sensitivity.py)、[真实结果记录](PROJECT_DOCUMENTATION.md)。

### 26. 准确率提升几道题是否有统计意义？如何避免挑出偶然有效的层？

**回答主线：** 看提升幅度，也看样本配对结构和实验选择过程；点估计领先不是稳定优于基线的充分证据。

**技术细节：** 对配对二元正确性，可在不一致的 `r+d` 条样本上做双侧精确二项检验，对应配对 McNemar 检验的精确思路。零假设下恢复与退化的机会各为 1/2。41 对 37 的改善很弱，实施记录中的近似 p 值约为 0.73；6 对 11 约为 0.33。后者虽然不显著，仍违反项目冻结的“净变化不得小于零”工程门禁。

项目采用 pilot、预注册晋级候选和 full-dev 复核来约束选择过程。更严格时还应处理多重比较、给出置信区间，并在未用于选模型的测试集上确认。确定性重复运行用于排除执行波动，不能扩大独立样本量或消除数据集选择偏差。

**可能追问：** 不显著是不是说明等价？不是，未拒绝差异为零不等于证明等价；等价或非劣性需要预先定义容忍边界与检验设计。

**代码与证据：** [层级确认流程](../src/quantization/layer_sensitivity_final.py)、[模块确认流程](../src/quantization/module_sensitivity_final.py)、[实施记录](PROJECT_DOCUMENTATION.md)。

### 27. 最终为什么选全 Linear INT4，而没有选 INT8 或保护敏感层的方案？

**回答主线：** 最终选择同时受质量、性能和证据完整性约束；算法更复杂或位宽更高，不代表更符合目标设备与负载。

**技术细节：** 实施记录中的三套真实制品结果如下，分数指对应集合的正确数：

| 候选 | full-dev | 高风险 | 长上下文 | Benchmark | 结论 |
|---|---:|---:|---:|---|---|
| `all_linear_int4` | 337/883 | 22/91 | 35/89 | 16/16，无 OOM | 当前门禁下唯一入选 |
| `all_linear_int8` | 341/883 | 24/91 | 39/89 | 15/16，1 项 OOM | 质量通过、性能失败 |
| `mixed_l10_mlp_lm_head_int8` | 332/883 | 23/91 | 36/89 | 16/16，无 OOM | full-dev 净退化，质量失败 |

门禁要求 full-dev 解析率至少 99%，三个质量集合净正确数不减少；性能要求相对 INT4 的峰值显存和最差 P95 比不超过 1.15，平均吞吐比不低于 0.85，且不能有 OOM。这里的“入选”限定于当前实验合同，不代表数值准确率已经满足银行生产要求。

**可能追问：** 是不是混合精度方向失败了？更准确地说，已验证的主保护候选失败；未评估候选不能一并判定。全 Linear INT4 本身也保留 BF16 特殊模块。

**代码与证据：** [筛选代码](../src/quantization/mixed_precision.py)、[门禁配置](../configs/mixed_precision_search.json)、[阶段报告](../out/stage7/report.md)、[详细结果](PROJECT_DOCUMENTATION.md)。

## 五、性能测量、容量与工程排障（28—34）

### 28. TTFT、TPOT、端到端延迟和吞吐有什么区别，项目怎么测？

**回答主线：** TTFT 反映首 token 等待，TPOT 反映后续生成速度，端到端延迟反映一次请求总耗时，吞吐反映单位时间产出；四者不能互相替代。

**技术细节：** runner 用 streamer 记录首个生成 token 的时刻，并在计时边界做 CUDA 同步。`TPOT ≈ (总耗时-TTFT)/(生成 token 数-1)`；batch 吞吐按 `batch_size × 每请求输出 token 数 / 秒数` 计算。固定最小和最大生成长度，排除提前结束的影响。

当前矩阵为 batch `[1,4,8,16]`、输入 `[128,512]`、输出 `[16,32]`，共 16 案例，每项预热 1 次、测量 5 次。输入 token 构建在计时开始前，因此这是模型生成路径测量，不涵盖网络、完整 tokenization 和在线排队。batch 级首 token 也不能直接当作多客户端各自 TTFT。

**可能追问：** 单 token 输出如何定义 TPOT？理论上没有后续 token 间隔，应视为不可定义；当前实现有分母保护，不能据此赋予它额外物理意义。

**代码与证据：** [计时与指标实现](../src/benchmark/runner.py)、[16 项矩阵](../configs/quantization_benchmark.json)。

### 29. 为什么 GPU 测速需要 synchronize、预热和重复采样？当前 P95 有什么局限？

**回答主线：** CUDA 通常异步提交操作，未同步的 CPU 时间可能只测到提交开销；首次执行还可能包含初始化、缓存和算子准备成本。

**技术细节：** 项目在关键计时点同步 CUDA，预热后重复测量，并报告延迟分布。测量环境还应控制其他 GPU 进程、功耗状态、版本和输入长度。runner 每次采样会清理 CUDA cache 并重置峰值统计，这有利于统一该实验的内存口径，但未必模拟长期在线服务的缓存行为。

只有 5 次测量时，P95 接近高端次序统计量的插值，稳定性有限，不应包装成生产尾延迟保证。正式服务压测需要更多请求、到达率、并发模型、冷暖启动区分、排队时间与失败率。可补充 CUDA event 或 profiler 分解 kernel 时间，但两者与用户端端到端时延回答的问题不同。

**可能追问：** 能否把 batch size 16 说成 16 并发用户？不能，固定同步 batch 与在线独立请求的调度和等待过程不同。

**代码与证据：** [采样与 percentile](../src/benchmark/runner.py)、[Benchmark 测试](../tests/test_benchmark_runner.py)。

### 30. 为什么模型压成 INT4 后，显存没有减少 75%？KV Cache 如何估算？

**回答主线：** 权重理论压缩比只是总显存的一部分，GPU 峰值还包含 cache、激活、临时 workspace、对齐和分配器开销。

**技术细节：** 粗略估算解码器 KV Cache 字节数：`2 × L × B × T × H_kv × D_head × bytes_per_element`。其中 2 表示 K 与 V，`L` 为层数，`B` 为 batch，`T` 为缓存长度。GQA 应使用 KV head 数，不能错用 Q head 数。BF16/FP16 每元素通常为 2 字节。

真实占用还受缓存布局、预分配、padding 和 allocator 影响。runner 同时记录估算与实际 cache 张量大小，并区分 `allocated`、`reserved`、`peak_allocated` 和增量峰值。制品文件大小又是另一口径。INT4 还有尺度与 packing 元数据，Embedding/Norm 保持 BF16，不能用“7B×0.5 字节”直接预测整机显存。

**可能追问：** 为什么长上下文时量化权重收益比例变小？因为 KV Cache 与激活占比随长度和 batch 增长，静态权重不再是唯一主项。

**代码与证据：** [KV 与显存测量](../src/benchmark/runner.py)、[特殊模块配置](../configs/mixed_precision_search.json)。

### 31. Benchmark 某个案例 OOM，应该停止、跳过还是算失败？

**回答主线：** OOM 是容量证据，应记录并继续收集其他案例；最终容量门禁仍必须失败，不能从汇总中悄悄删除失败负载。

**技术细节：** runner 捕获 `torch.OutOfMemoryError`，保存 `case_id`、输入输出长度、batch、异常和失败时显存，标记 `status=oom`，清理可释放缓存后继续。最终筛选检查 `oom_case_count==0`。真实 INT8 在 `bs16-in512-out32` 失败，即使前 15 项完成也不满足原矩阵。

项目曾出现 OOM 处理器自身引用未绑定 `torch` 的二次异常，修复为在 runner 入口明确取得 `service.torch`。这是典型的“异常路径也必须测试”。进一步可以按案例增量落盘，避免进程后期失败导致已完成测量尚未写出；这是改进方向，不应说当前已完全实现。

**可能追问：** 能不能减少 batch 让它通过？可以建立新的容量合同重新比较，但不能偷偷修改既定工作负载并沿用旧结论。

**代码与证据：** [OOM 处理](../src/benchmark/runner.py)、[异常回归测试](../tests/test_benchmark_runner.py)、[最终门禁](../src/quantization/mixed_precision.py)。

### 32. 当前性能门禁为什么存在跨 workload 比较偏差，应该怎么修？

**回答主线：** 先分别取两个方案跨案例的最大值再相除，可能比较了不同负载，掩盖某个特定案例的严重退化。

**技术细节：** 当前 `_benchmark_summary()` 对成功案例取最大峰值显存、最大 P95，再计算候选与基线比率。假设基线在 A/B 的 P95 为 100/50 ms，候选为 110/80 ms，最大值比只有 1.10，但 B 的同案例比为 1.60。若合同要求每个 workload 都不超过 1.15，这种汇总会误放行。

更合理的后续实现是按 `case_id` 对齐，验证案例集合、负载参数和测量配置一致，再分别计算显存、延迟和吞吐比；缺失或 OOM 明确失败。是否每项都需通过，还是允许按真实流量加权，应提前定义。现有结果记录指出主混合精度最差同案例 P95 比为 1.234，说明这个问题具有实际影响。

**可能追问：** 是否要重跑 GPU 才能修？已有完整同口径案例报告时，可以先修离线比较与报告；只有证据缺失或不一致才需重跑。

**代码与证据：** [当前汇总函数](../src/quantization/mixed_precision.py)、[改进队列](TODO.md)、[配对性能记录](PROJECT_DOCUMENTATION.md)。

### 33. 为什么用 meta 模型骨架加载量化 state_dict 会失败？assign=True 为什么救不了？

**回答主线：** meta tensor 只有形状等元信息，没有真实数据；state_dict 不包含所有运行时 buffer，所以并非加载完权重就恢复了完整模型。

**技术细节：** RoPE 等模块可能注册 `persistent=False` 的 buffer，不写入 state_dict。用 meta 骨架后，`load_state_dict(assign=True)` 只替换 state_dict 中存在的参数和持久 buffer；非持久 buffer 仍在 meta，整模型 `.to(cuda)` 就可能报 `Cannot copy out of meta tensor`。

项目改成先在 CPU 正常构建 BF16 骨架，使非持久 buffer 正确初始化，再将量化 state_dict 映射到目标设备，用 `assign=True` 替换对应权重，检查 missing/unexpected keys，最后搬运剩余 buffer。代价是增加 CPU 内存峰值。单纯 `to_empty()` 只分配空间，不保证恢复了 RoPE 等 buffer 的正确数值。

**可能追问：** 为什么不是重新导出？该问题发生在加载阶段，已验证哈希的量化制品可能完全正常，应先修加载流程，避免无意义重算。

**代码与证据：** [load_mixed_precision_service](../src/quantization/mixed_precision.py)、[故障记录](PROJECT_DOCUMENTATION.md)。

### 34. 大模型制品保存失败、断点续跑和证据过期怎么处理？

**回答主线：** 保存需要完整性标记，续跑需要验证输入与产物合同，不能只看到目录存在就判断成功。

**技术细节：** 当前量化权重先写 `.partial` 临时文件，完成后重命名，再生成包含 SHA256 的 manifest。写入失败会清理对应临时文件并提示检查磁盘空间、inode、quota 或更换输出目录。manifest 最后写出，可以降低半成品被误当成功制品的风险。

应准确描述保证边界：同文件系统 rename 能提供文件替换原子性，但不等于整套模型目录是数据库事务；当前重导出逻辑会删除已有权重文件，不能宣称“任何失败都完整保留旧版本”。更稳妥的后续方案是每次导出到新版本目录，验证完毕后原子更新版本指针。证据登记与收口还需要检查哈希、候选合同和各 suite 的完整性。

**可能追问：** SHA256 一致就一定能加载？不一定，还受架构、依赖与 Tensor 子类反序列化兼容性影响，所以独立重载验证不可省略。

**代码与证据：** [制品保存与证据检查](../src/quantization/mixed_precision.py)、[断点执行脚本](../scripts/run_mixed_precision_search.sh)。

## 六、结构化剪枝、业务诊断与后续交付（35—40）

### 35. 结构化剪枝与非结构化剪枝有什么区别？为什么参数置零不一定加速？

**回答主线：** 结构化剪枝直接改变矩阵维度、head 或层数；非结构化剪枝通常只是增加零值，需要专门稀疏布局与 kernel 才可能获益。

**技术细节：** 普通 dense GEMM 不会因为矩阵里多了零就自动减少乘加，因此 mask 的稀疏率不能等同于延迟下降。项目剪枝实现会创建新的 Linear 并切片复制保留权重，实际删除 Attention 或 MLP 维度；层剪枝则重建 ModuleList。

N:M 稀疏如 2:4 要求特定分组中保留规定数量的非零值，还需设备、维度和算子支持。当前不能把它作为已经交付的实测加速成果。剪枝评测也要单独报告目标剪枝率、实际参数减少率、真实文件大小与性能，形状对齐可能让四档目标率对应的实际比例不同。

**可能追问：** 结构化剪枝是否一定降低延迟？也不一定，改变后的维度可能降低 kernel 利用率；必须重新 benchmark。

**代码与证据：** [结构化剪枝实现](../src/pruning/structured.py)、[剪枝配置](../configs/structured_pruning.json)。

### 36. Qwen 的 GQA Attention 如何剪枝，为什么不能按百分比随意删 head？

**回答主线：** GQA 的 Query head 与 KV head 存在分组关系，剪后要保持结构合法，且避免 KV 被不成比例地破坏。

**技术细节：** 当前配置针对 28 个 Q head、4 个 KV head 的架构。合法形状至少满足 `Hq % Hkv == 0`，两者为正，head_dim 与投影维度一致。保留 Q head 时同步切 `q_proj` 输出行和 `o_proj` 输入列；保留 KV head 时同步切 `k_proj/v_proj` 输出行。

`feasible_gqa_shape()` 枚举合法形状，其目标包含实际宽度削减与目标率的偏差，以及 Q/KV 削减率失衡惩罚。否则仅优化总宽度接近 10%，可能选出 Q 不变而 KV 从 4 减到 1 的极端解。合法性也不是语义无损证明，head 重分组后的质量仍需真实评测。

**可能追问：** 为什么强调显式 `head_dim`？若运行时仍按 `hidden_size/num_heads` 推导，删 head 后会错误改变 head_dim，导致重载后的 shape 或 forward 失败。

**代码与证据：** [GQA 形状搜索与投影切片](../src/pruning/structured.py)、[结构约束配置](../configs/structured_pruning.json)。

### 37. SwiGLU MLP 和 Transformer 层剪枝怎样保持模型可运行？

**回答主线：** 必须同时修改相互依赖的投影与配置，并以保存后的独立重载验证闭环，不能只验证内存里的对象能 forward。

**技术细节：** SwiGLU 可表示为 `down(SiLU(gate(x)) ⊙ up(x))`。若保留中间通道集合 `I`，必须同时保留 gate/up 的输出行与 down 的输入列。项目使用权重 L2 重要性，并将中间维度按 128 对齐，保证三个投影的通道一致。

层剪枝需重建层列表、更新 `num_hidden_layers`，并重编影响 cache 的 `layer_idx`。结构验收检查 Q/K/V/O shape、GQA 整除关系、MLP 对齐和模型 config，一次单 token forward 后保存，再从磁盘重载后二次 forward。配置要求支持显式 head_dim 的运行环境；这个版本要求是仓库约束，不应被泛化成所有 Qwen 实现的普遍边界。

**可能追问：** 为什么单 token forward 仍不够？它主要证明基础可执行性，完整生成、cache 增长、长上下文质量和性能仍需单独测试。

**代码与证据：** [prune_mlp、prune_layers 与 export_candidate](../src/pruning/structured.py)、[剪枝测试](../tests/test_structured_pruning.py)。

### 38. 怎样判断剪枝质量拐点，剪枝和量化应该谁先谁后？

**回答主线：** 按预注册比例逐档实验，使用同源基线与相同质量口径判断；剪枝与量化的顺序也是实验变量，不能凭经验宣布固定最优顺序。

**技术细节：** 项目注册 5%、10%、15%、20% 四档，质量门槛是相对同源 BF16 的绝对准确率下降不超过 0.02，即 2 个百分点，并要求解析率至少 99%。四个候选导出和质量证据齐全后，收口流程才记录首个超过阈值的档位。由于合法维度离散化，应同时展示实际参数减少率。

一种后续路线是先结构剪枝、必要时恢复训练，再校准量化，因为剪枝改变激活分布；如果先量化再剪枝，原 scale 与 packing 可能失效，需要重新构建。质量对剪枝率不保证单调，所以“首个超阈值档位”只是该离散实验的定义，不能宣称发现连续数学意义上的唯一拐点。当前仓库尚不能给出完整 7B 四档实测结论。

**可能追问：** 下降 2% 是相对比例还是百分点？配置使用绝对准确率差，40% 到 38% 是下降 2 个百分点、相对下降 5%。

**代码与证据：** [剪枝配置与门槛](../configs/structured_pruning.json)、[证据收口](../src/pruning/structured.py)、[实施状态](PROJECT_DOCUMENTATION.md)。

### 39. 金融错误定位如何避免“整体准确率提升，但关键业务更差”？

**回答主线：** 用业务分类、逐样本配对和不可评估状态表达结论，避免把不同风险的错误简单平均。

**技术细节：** `financial_error_localization` 对输入预测建立索引，结合类别信息分析金额、利率/比例、日期/期限、结构化输出与引用等错误，并保存输入输出哈希。对主混合精度候选，实施记录中金额、利率/比例、日期/期限分别净退化 5/2/6 题。类别可能重叠，不能把三个数直接相加当作总退化题数。

某些安全类别需要专门标签，L1/L3 也不是当前 FinQA 主场景已充分覆盖的业务。缺少适用数据应报告 `not_evaluable`，而不是“错误数为零所以通过”。结构化引用格式正确也不等于证据事实正确。这样可以明确区分已检测问题、未发现问题和根本没有评估能力。

**可能追问：** 怎么将错误映射回层？先通过精度恢复消融观察变化，再用样本、激活和模块证据解释；单个错误类别相关性不能自动定位唯一责任层。

**代码与证据：** [金融错误定位](../src/evaluation/financial_error_localization.py)、[定位报告](../out/financial_error_localization/report.md)、[阶段边界](../out/stage7/report.md)。

### 40. 如果继续推进到真实部署，你最优先做什么？如何验证交付和成本收益？

**回答主线：** 先修正影响决策的评测口径，再完成目标后端的在线验证；以可验证的质量、容量和单位成本定义交付。

**技术细节：** 第一优先级是按相同 `case_id` 配对性能，并明确所有子集是否都要求 99% 解析率。当前门禁仅对 full-dev 检查这一门槛，不能默认覆盖长上下文。然后补独立测试、更多重复测量和线上请求分布，验证实际服务的排队、并发、TTFT、P95/P99、失败率与稳定性。

接入 vLLM 或 TensorRT-LLM 时，需要重新验证权重格式、kernel、KV 管理和连续批处理，不能假定 TorchAO `.pt` 可直接复用。昇腾需在真实硬件上登记 CANN/驱动/后端版本并独立校准与测量；当前它仍是待完成能力。

成本可用 `实例每小时成本 / 每小时成功输出 token 数 × 10^6` 表示每百万输出 token 成本，并明确输入 token、利用率、冗余和失败请求的核算方式。上线前还需版本指针、灰度流量、质量与延迟告警和回滚演练。已有单测应验证 shape、哈希、门禁与异常路径；另补真实导出→重载→生成→业务回归的 GPU 集成测试。上述是后续交付计划，不能作为现有上线成果。

**可能追问：** 这个项目最有价值的经验是什么？把“配置声称有效”“张量确实改变”“真实制品可重载”“业务质量不退化”“目标负载有收益”分成独立证据层，逐层验证。
