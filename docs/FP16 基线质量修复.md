# 表格问答质量改进说明

## 一、这几项工作整体上是在做什么

这四项工作是在建立一条可验证的表格问答质量链路：

1. 先确认模型读取的是不是正确的表格单元格；
2. 再确认证据、公式、结果和单位是否一致；
3. 按不同计算题型分别统计，定位具体弱点；
4. 如果仅靠 Prompt 仍无法解决，再考虑使用 FinQA train 做 LoRA 微调。

核心目的不是单纯追求一个更高的总体准确率，而是能够回答：**错在取数、公式、计算、单位，还是模型的任务能力不足。**

## 二、给表格行列增加稳定 ID 是什么意思

稳定 ID 是给每一行、每一列，以及必要时给每一个单元格分配一个不会随显示顺序变化而改变的标识。

例如，一个单元格可以表示为：

```text
row_id=经营利润
col_id=2023
cell_id=经营利润_2023
```

它的作用不是让表格更好看，而是让系统在处理、引用和评估时始终指向同一个对象。

### 为什么需要稳定 ID

- 表格中可能存在重复名称，例如两列都叫“合计”，仅靠文字无法唯一定位。
- 表格经过排序、筛选、合并或分页后，行号和列号可能发生变化。
- 模型输出的 `operands`、`evidence` 和计算过程需要回指原表格。
- 稳定 ID 可以把“引用错了单元格”变成机器可检查的 ID 不匹配问题。

## 三、四项工作的具体含义

### 1. 验证 `operands` 是否真的来自对应表格单元格

`operands` 指运算时使用的输入值，例如计算增长率时使用的“本年收入”和“上年收入”。

需要检查：

- 每个输入值是否真的存在于模型引用的单元格中；
- 行、列、年份是否对应；
- 数值和单位是否一致；
- 引用的 `cell_id` 是否与实际单元格匹配。

#### 为什么要做

表格问答中常见的错误不是不会计算，而是拿错了数字。如果输入值一开始就来自错误单元格，那么后面的公式即使正确，最终答案仍然是错的。

### 2. 检查 `evidence`、`operation`、`value`、`unit` 是否一致

这四个字段可以理解为一条完整的推理链：

| 字段 | 含义 |
|---|---|
| `evidence` | 支持答案的表格证据单元格 |
| `operation` | 对输入数据执行的运算，例如加法、除法或求平均 |
| `value` | 运算得到的结果 |
| `unit` | 结果的单位，例如元、人数或百分比 |

检查重点是：证据是否支持输入，运算是否符合题意，结果能否复算，单位是否在过程中保持一致。

例如，题目问“增长率”时，通常需要使用“差值 ÷ 前期值”的运算，结果应当以百分比表示。如果把金额直接当成百分比，或把“平均”误做成“总和”，就属于字段之间不一致。

#### 为什么要做

只看最终答案，往往无法判断问题在哪里。把这四个字段放在一起核对，可以区分：

- 取数错误；
- 公式错误；
- 算术错误；
- 单位错误。

这样才能知道应该修改表格解析、Prompt 还是模型本身。

### 3. 对百分比、平均、总和、多步题单独统计

不能只看一个总体准确率，因为简单题可能会掩盖某类题型的明显弱项。建议至少分别统计以下四类：

| 题型 | 典型任务 | 单独统计的意义 |
|---|---|---|
| 百分比 | 增长率、占比、变化幅度 | 检查分母、百分号和四舍五入是否正确 |
| 平均 | 平均成本、平均人数、均值比较 | 检查除数、样本范围和空值处理 |
| 总和 | 合计、累计、跨年度求和 | 检查是否重复计入小计行或合计行 |
| 多步题 | 先求差值，再求比例或换算单位 | 观察中间结果是否正确传递到下一步 |

#### 为什么要做

分题型统计可以回答：

- 是表格读取能力不足，还是基础运算不稳定？
- 是百分比题特别容易错，还是多步推理容易丢失中间结果？
- Prompt 优化后，究竟是哪一类题型得到了改善？

### 4. 如果 Prompt 优化仍不够，再使用 FinQA train 做 LoRA 微调

Prompt 优化是通过改进指令、输出格式和检查步骤来提升表现。LoRA 微调则是在基础模型上训练一组较小的参数，使模型更适应 FinQA 这类表格推理任务。

这里的“如果仍不够”是一个门槛：应先证明问题不是仅靠提示词和流程设计就能解决，再考虑训练。

#### 为什么不一开始就微调

- 微调成本更高，需要准备数据、训练、验证和回滚方案。
- 如果根因是表格解析或字段对齐错误，微调无法修复错误输入。
- 过早微调可能把训练数据中的偏差学进去，导致新表格上的泛化能力变差。
- 先建立 Prompt 基线，才能判断 LoRA 带来的真实增益。

## 四、推荐执行顺序

1. **固定表格结构**：为行、列和单元格生成稳定 ID，并将 ID 写入中间表示。
2. **核验引用**：检查 `operands` 是否能回指正确的 `cell_id`，并记录错误类型。
3. **核验一致性**：对 `evidence`、`operation`、`value`、`unit` 进行规则检查和结果复算。
4. **按题型评估**：分别报告百分比、平均、总和、多步题的准确率和主要错误。
5. **对比干预效果**：先比较原始 Prompt 和优化 Prompt；如果仍存在稳定、可重复的模型能力缺口，再使用 FinQA train 做 LoRA，并保留独立验证集。

## 五、一句话总结

这四项工作构成一条从数据到模型的排错链：先确认“读的是哪一个格子”，再确认“证据、公式、结果和单位是否一致”，然后按题型定位弱点，最后才决定是否需要 LoRA。这样可以用更小的成本找到真正的瓶颈，并让每一次优化都能被验证、比较和复现。

## 六、4080 pilot 暴露的问题与下一轮代码优化

### 6.1 当前 pilot 的结论

在 4080 上使用 Qwen2.5-3B-Instruct、相同的 80 条样本和相同生成参数，对照结果为：

| 方案 | 解析率 | 数值准确率 | 正确数 |
|---|---:|---:|---:|
| `structured_json` | 93.75% | 15.00% | 12/80 |
| `evidence_operation` | 72.50% | 10.00% | 8/80 |

`evidence_operation` 虽然有 58 条样本进入了确定性计算器，但没有提高正确数。主要失败点是模型引用了错误的
单元格、把除法的分子和分母反了、输出错误数量的操作数，或在 JSON 后继续生成解释文本。因此下一轮不再只
修改文字 Prompt，而是把表格引用和操作规则变成程序可以拒绝的约束。

### 6.2 稳定单元格 ID

`src/evaluation/quality_repair.py` 新增 `add_stable_table_ids()`。当方案启用 `stable_cell_ids` 时，表格中
每个单元格都会被标记为：

```text
[cell_id=r3c4] 290.6
```

其中 `r3` 是表格行索引，`c4` 是列索引。模型必须在 evidence 中返回同一个 ID 和原始单元格值：

```json
{
  "evidence": [{"cell_id": "r3c4", "value": "290.6"}],
  "operands": [290.6, 303.1],
  "operation": "subtract",
  "unit": "million"
}
```

这样做的原理是把“我认为这个数字来自某一行”变成“我引用了明确的 `rNcM` 单元格”。程序可以检查 ID 是否
存在、引用值是否与原表格相同，从而拦截模型凭空编造数字或引用错误单元格的情况。

### 6.3 操作数、操作类型和单位校验

新增 `validate_evidence_operation()`，在计算前执行以下检查：

1. evidence 必须是包含 `cell_id` 和 `value` 的对象；
2. `cell_id` 必须符合 `rNcM` 格式，并且存在于当前表格；
3. evidence 中的数值必须与真实单元格数值一致；
4. 每个 operand 必须来自 evidence 的数值单元格；
5. 减法、除法、比例、百分比变化和绝对差必须恰好有两个 operand；
6. 加法和乘法至少需要两个 operand；
7. 百分比变化、百分比和 percentage 操作必须使用百分比单位。

校验通过后，才允许 `Decimal` 计算器执行结果。校验不通过时不使用模型生成的最终数字，记录
`validation_error`，并将错误原因加入一次定向重试 Prompt。

### 6.4 为什么只重试证据和操作数

旧逻辑在格式失败时让模型重新生成完整回答，模型可能再次改变公式、答案和解释，导致错误范围扩大。新逻辑
把重试目标限制为：

```text
合法 cell_id + 正确 cell value + 正确 operands + 合法 operation
```

计算仍然由程序完成。这样可以把重试从“重新回答整道题”变成“修复一个明确的结构错误”，降低输出漂移。

### 6.5 本轮修改涉及的文件

- `configs/quality_repair_4080.json`：启用 `stable_cell_ids`，更新 evidence-operation 输出契约；
- `src/evaluation/quality_repair.py`：增加稳定 ID、单元格回指校验、操作数数量校验、单位校验和定向重试；
- `tests/test_quality_repair.py`：增加合法引用、错误单元格值和错误操作数数量测试；
- `docs/TODO.md`：将代码实现标记完成，将 4080 复测保留为待办。

### 6.6 下一步执行原则

这轮代码改变的是“模型输出后如何被验证”，不是已经得到质量提升。需要在同一批 80 条样本上重新运行
`structured_json` 和启用稳定 ID 的 `evidence_operation`，重点观察：

- 结构化解析率是否回到 90% 以上；
- `validation_failure_count` 是否下降；
- 百分比和除法题的正确数是否增加；
- 正确数是否超过旧方案的 12/80。

只有新方案同时减少校验失败并提高正确数，才继续扩展到完整 883 条 dev；否则继续优化表格证据表示，暂不进行
LoRA 微调。

## 七、稳定 ID 复测结果与调整结论

### 7.1 复测结果

第二轮在同一批 80 条样本上运行了带稳定 ID 和一致性校验的新代码，输出目录为
`out/quality_repair_3b_4080_v2`：

| 方案 | 解析率 | 数值准确率 | 正确数 | 校验失败数 | 重试次数 | 用时 |
|---|---:|---:|---:|---:|---:|---:|
| `structured_json` | 93.75% | **15.00%** | **12/80** | 0 | 23 | 302.8 秒 |
| 带稳定 ID 的 `evidence_operation` | 6.25% | 2.50% | 2/80 | 75 | 78 | 384.7 秒 |

这说明校验器本身在工作：80 条中有 75 条输出被识别为不满足单元格、操作数或单位约束。但“能识别错误”不等于
“模型已经能按约束输出”。新方案相较上一轮 `evidence_operation` 的 8/80 正确数进一步下降到 2/80，不能进入
完整 883 条评测。

### 7.2 失败类型

校验失败主要集中在：

- 39 条无法解析为完整 evidence-operation 对象；
- 24 条 operands 没有从 evidence 数值单元格复制；
- 6 条 cell ID 不存在或 cell value 与真实表格不一致；
- 2 条百分比变化缺少百分比单位；
- 少量样本的减法只有一个 operand。

这暴露出一个新的问题：对 3B 模型来说，“输出 cell_id、精确 value、operands、operation、unit”同时满足的契约
过于复杂。稳定 ID 解决了可验证性，但增加了生成负担，导致格式失败和重试次数显著上升。

### 7.3 下一轮调整原则

下一轮不直接把严格 schema 继续加长，而是保留稳定 ID作为内部校验信息，并降低模型必须生成的字段数量：

1. evidence 仍要求引用合法 `cell_id` 和原始值；
2. operands 改为可选，若 evidence 中恰好包含满足操作所需数量的数值，则由程序安全恢复 operands；
3. 缺失的百分比单位根据 operation 做受限归一化，不接受任意模型生成单位；
4. 只有操作数数量明确、证据值真实存在、除数非零时才允许计算；
5. 无法安全恢复时标记为不可解析，不使用模型解释文本中的数字；
6. `structured_json` 继续作为同一批样本的固定对照组。

这种调整的原理是把“模型必须生成的结构”与“程序可以确定恢复的结构”分开。模型只负责选择证据和操作类型，
程序在证据充分且无歧义时补齐操作数；如果证据不足，程序宁可拒绝计算，也不猜测答案。这样可以降低输出负担，
同时保留单元格回指和确定性计算的质量保护。

## 八、`cell_ids_operation` 紧凑方案

为降低上一轮输出契约的复杂度，代码新增 `cell_ids_operation` 方案。模型只需要输出：

```json
{
  "cell_ids": ["r3c4", "r3c5"],
  "operation": "subtract",
  "unit": "million"
}
```

模型不再重复生成 evidence 数值和 operands。程序根据原始表格中的 `cell_ids` 自动查找真实单元格值，按
cell_id 顺序生成 operands，再交给 `Decimal` 计算器。这样可以同时消除“evidence 值抄错”和“operands 与
evidence 不一致”两类错误。

`structured_json` 仍然保留为对照方案，4080 默认对比：

```bash
python3 scripts/run_quality_repair_4080.py \
  --model-path /userhome/cs5/u3680889/OptimizationSystem/models/Qwen2.5-3B-Instruct \
  --model-id Qwen/Qwen2.5-3B-Instruct \
  --dataset-dir /userhome/cs5/u3680889/OptimizationSystem/datasets \
  --output-dir out/quality_repair_3b_4080_v3 \
  --variants structured_json,cell_ids_operation
```

本方案仍然会检查 cell_id 是否存在、数量是否符合 operation、对应单元格是否为数字以及百分比单位是否合理。
只有所有检查通过，程序才会恢复 operands 并计算；格式错误或引用不明确时不会读取模型解释文本中的数字。

## 十、语义化 cell ID 与结构化回退

v3 仍然显示裸 `rNcM` ID 对 3B 模型不够友好，因此下一版在表格显示中加入行名、列名和年份：

```text
[cell_id=r3c4 row=weighted average shares column=2017] 290.6
```

模型输出仍只包含短的 `cell_ids`、`operation` 和 `unit`，但可以利用旁边的财务语义选择正确单元格。程序内部
仍使用原始 `rNcM` ID 查表，不把模型生成的行名或列名当作数值来源。

同时，`cell_ids_operation` 增加 `fallback_to_structured`：当 cell ID 不存在、引用的单元格不是数字、操作数量不对
或 JSON 无法解析时，程序额外请求一次原有 `structured_json` 格式。回退结果独立解析，不读取 cell-id 输出中的
解释文本数字，并在预测记录中写入 `fallback_used` 和 `validation_error`。

回退的原理是保留新方案的可验证性，同时避免一次严格契约失败就丢弃整个样本。`structured_json` 仍然是主对照；
只有混合结果超过 `12/80`，才有必要进入完整 dev 评测。

## 十一、`cell_ids_operation` v4 复测结果

### 11.1 指标

第四轮在同一批 80 条样本上运行了语义化 cell ID 和 structured 回退，结果位于
`out/quality_repair_3b_4080_v4`：

| 方案 | 解析率 | 数值准确率 | 正确数 | 校验失败数 | 回退次数 | 用时 |
|---|---:|---:|---:|---:|---:|---:|
| `structured_json` | 93.75% | **15.00%** | **12/80** | 0 | 0 | 303.4 秒 |
| `cell_ids_operation` + 回退 | 85.00% | 13.75% | 11/80 | 21 | 21 | 352.1 秒 |

语义化提示显著改善了上一轮的 `71.25%` 解析率，回退也成功挽回了 3 条正确答案；但最终仍比
`structured_json` 少 1 条正确答案。因此当前方案接近基线但尚未超过基线，不能进入完整 883 条评测。

### 11.2 错误定位

`cell_ids_operation` 直接计算正确 8 条，回退后额外正确 3 条。剩余错误主要是：

- 15 条输出无法形成完整 operation 对象；
- 少量 cell ID 指向文字标签、年份或不存在的列；
- 百分比变化的方向仍可能反转；
- 新方案用时比 `structured_json` 多约 49 秒，主要来自失败后的额外回退请求。

### 11.3 结论

当前最优稳定方案仍是 `structured_json` 的 `12/80`。下一步的高价值方向不再是增加输出字段，而是：

1. 根据问题关键词做题型路由；
2. 对百分比、除法和变化题生成有限的操作方向候选；
3. 用证据一致性和问题语义做候选选择；
4. 只有候选方案超过 `12/80`，才继续完整评测或 LoRA 微调。

## 九、`cell_ids_operation` v3 复测结果

### 9.1 指标对比

第三轮在同一批 80 条样本上运行了 `structured_json` 和 `cell_ids_operation`，结果位于
`out/quality_repair_3b_4080_v3`：

| 方案 | 解析率 | 数值准确率 | 正确数 | 校验失败数 | 重试次数 | 用时 |
|---|---:|---:|---:|---:|---:|---:|
| `structured_json` | 93.75% | **15.00%** | **12/80** | 0 | 23 | 302.7 秒 |
| `cell_ids_operation` | 71.25% | 7.50% | 6/80 | 23 | 37 | 255.5 秒 |

相比上一轮严格 `evidence_operation` 的 2/80，紧凑契约将正确数提升到 6/80，解析率也从 6.25% 提升到
71.25%，说明减少重复字段确实有效。但它仍低于 `structured_json` 的 12/80，暂时不能作为主方案。

### 9.2 当前剩余瓶颈

这一轮的主要错误已经从“输出字段太多”转移到“选错单元格和操作方向”：

- 模型有时引用表格中的文字标签或年份单元格，程序因此拒绝非数字 cell；
- 有些输出只生成 `cell_ids`，没有稳定生成 operation；
- 百分比和比例题仍容易把分子、分母顺序弄反；
- `cell_ids` 是裸的 `rNcM`，模型需要依赖行列位置计数，缺少财务语义提示。

### 9.3 下一轮优化方向

下一轮不再增加输出字段，而是改进输入表示和方案组合：

1. 在表格显示中同时给 cell_id 附加行名、列名和年份，例如
   `[cell_id=r3c4 row=weighted average shares column=2017] 290.6`；
2. 根据问题中的 `percent`、`average`、`total`、`change` 等关键词做题型路由，限制可选 operation；
3. 对 `cell_ids_operation` 校验失败的样本触发 `structured_json` 回退，避免新方案格式失败时直接丢失基线答案；
4. 对除法和百分比变化显式检查新旧年份顺序，并记录候选方向；
5. 只有混合方案超过 `structured_json` 的 12/80，才运行完整 883 条评测。

## 十二、题型路由与候选 JSON 校验（下一轮）

为解决 v4 中“格式已经解析，但单元格或运算方向选错”的问题，代码新增
`routed_cell_ids_operation` 方案。它不改变最终输出契约，仍只要求模型返回
`cell_ids`、`operation` 和 `unit`，但在请求后追加三类约束：

1. **题型路由提示**：根据问题中的 `percentage`、`ratio`、`average`、`total`、`change`
   等词，提示应使用 `divide`、`percent_change`、`average`、`add` 或按时间顺序
   `subtract`；百分比结果保持为分数，避免额外乘以 100。
2. **合法数值单元格清单**：把当前表格中可解析为数字的 cell ID 和原始值列成短清单，
   降低模型引用年份、行名或不存在 ID 的概率。
3. **多候选校验**：小模型经常在一次输出中生成多个 JSON。解析器逐个候选执行真实表格
   校验，优先采用第一个 cell ID、数量、数值类型和 operation 都通过的候选，而不是无条件
   采用第一个 JSON。
